# IntelliVNG 概念建模设计与演进思考

> **写在前面**
> 
> 在构建 IntelliVNG 时，我们并没有一开始就去定义 JSON Schema。相反，我们花了很多时间去思考一个更本质的问题：**"一个人类编剧团队是如何创作一部非线性非线性视觉小说游戏的？"**
> 
> 本文尝试还原我们的探索路径：从解构非线性视觉小说游戏的创作本质，到推导核心数据模型，再到设计 Agent 协作范式。这是一场关于如何将"艺术创作直觉"转化为"工程化数据结构"的思维实验。

## 第一章：寻找创作的"原点" —— 核心概念建模

在系统设计的初期，我们面临的第一个挑战是：**如何定义输入？**

最简单的做法是给 LLM 一个 Prompt："写一个校园冒险游戏剧本"。但根据我们对大量优秀非线性视觉小说游戏（如`《逆转裁判》、《底特律：变人》、《完蛋！我被...》`）的调研，发现决定一部作品上限的，往往不是具体的对话，而是底层的**设定地基**。

为了让 AI 的创作不至于"天马行空但空洞无物"，我们从人类创作方法论中提炼出了 **四个核心维度** ，作为系统的**WorkflowInput（工作流起点）**：

### 1. WorldBible（世界观圣经）：沉浸感的边界
- **思考**：为什么 AI 写的故事容易"出戏"？
- **发现**：因为 AI 缺乏"常识边界"。它可能前一秒还在写古代宫廷，后一秒就出现了手机。
- **设计推导**：我们需要一个**WorldBible**。它不仅是背景介绍，更是**规则集（Rules）**。它定义了物理法则（有无魔法？）、社会结构（等级制度？）和可用场景池。
- **作用**：这成为了后续所有 Agent 的"宪法"。Planner 规划剧情时不能违背物理法则，Writer 描写场景时必须从场景池中取材，确保了逻辑的一致性。

### 2. CharacterDB（角色数据库）：驱动剧情的引擎
- **思考**：什么是好的非线性叙事？
- **发现**：好的分支不是为了分而分，而是**基于性格的选择**。
- **设计推导**：简单的"姓名/年龄"是不够的。我们在 **CharacterDB** 中引入了两个关键字段：
    - **`personality.traits` (性格标签)**：决定了角色"怎么说话"。
    - **`coreTraits.obsession` (核心执念)**：决定了角色"怎么做选择"。**
- **作用**：当 Node Writer 撰写对话时，它不再是随机生成，而是基于"执念"进行角色扮演。

### 3. StyleGuide（风格指南）：统一叙事的调性
- **思考**：多 Agent 协作最大的风险是什么？
- **发现**：是"风格割裂"。Planner 想要赛博朋克风，Writer 却写成了青春疼痛文学。
- **设计推导**：我们需要一个显式的 **StyleGuide**，包含 `tone` (基调) 和 `themes` (主题标签)。
- **作用**：它是 Agent 间的"对齐信号"，确保所有生成的文本在氛围上保持高度统一。

### 4. Constraints（工程约束）：落地的保障
- **思考**：这是游戏，不是纯小说。
- **发现**：游戏开发有资源限制（美术资源有限、工期有限）。
- **设计推导**：引入 **Constraints**，明确 `targetNodeCount`（节点预算）和 `targetEndingCount`（结局预算）。
- **作用**：这迫使 Story Planner 戴着镣铐跳舞，在有限的资源内通过结构设计最大化叙事张力，而不是无限制地发散。

## 第二章：从"上帝视角"到"专业分工" —— Agent 架构演进

有了坚实的输入地基，我们满怀信心地进入了执行层设计。最初的设想，也是最诱人的想法是：**"创建一个无所不能的'上帝 Agent'，用一个完美的 Prompt 包办一切。"**

### 1. "上帝 Agent"的黄昏：一次惨痛的失败
我们尝试将所有需求——故事规划、对话撰写、多结局设计、JSON 格式化——全部塞进一个长达 500 行的 System Prompt 中。我们称之为"全能导演（Director King）"方案。

结果是彻底的失败。我们观察到了几个反复出现的"AI 创作病"：

*   **结构性遗忘**：AI 在撰写第 10 个节点时，已经完全忘记了第 1 个节点埋下的伏笔。这就像一个记忆只有七秒的编剧，故事无法形成逻辑闭环。
*   **创造力坍塌**：当要求过多时，AI 会选择最"安全"的路径来完成任务。我们要求"多分支"，它就在故事的最后设置一个选择题，通向三个几乎没区别的结局。这是一种"为了分支而分支"的**伪非线性**。
*   **顾此失彼**：当 AI 专注于构建复杂的分支逻辑时，它会忽略对话的质量；而当它沉浸于角色扮演时，又会忘记格式化输出的要求。这就像要求一个人同时扮演导演、编剧、演员和场记，结果必然是一团糟。

### 2. "Aha Moment"：我们在模拟一个"人类编辑部"
这次失败让我们意识到，我们试图让一个 Agent 去解决一个需要**不同思维模式**的复杂问题。
*   **规划**需要**宏观、结构化**的思维。
*   **写作**需要**微观、沉浸式**的思维。
*   **审阅**需要**批判性、分析性**的思维。

真正的突破来自于一个简单的类比：**"一个成熟的编辑部是如何运作的？"**

他们不会把所有工作都交给一个人。他们有明确的**专业分工**：

1.  **总编 / 策划 (The Architect)**：他负责敲定选题、规划故事大纲、设计核心冲突和结局走向。他关心的是"骨架"是否坚固，不关心具体的遣词造句。
2.  **作者 / 写手 (The Writer)**：他拿到大纲后，负责将每个章节填充成有血有肉的文字。他关心的是对话是否精彩、角色是否鲜活。
3.  **责任编辑 / 监修 (The Guardian)**：他负责审阅初稿，检查是否有逻辑漏洞、人物是否 OOC (Out of Character)、节奏是否拖沓。

这个类比让我们豁然开朗。我们需要的不是一个"上帝"，而是一个**团队**。于是，IntelliVNG 的三位一体 Agent 架构诞生了：

*   `Story Planner` 对应 **总编**，负责宏观结构。
*   `Node Writer` 对应 **写手**，负责微观填充。
*   `Story Reviewer` 对应 **监修**，负责质量保障。

### 3. Agent 的"天职"：清晰的职责边界
这种分工的价值在于**职责的限定**。我们为每个 Agent 定义了清晰的"天职"：

| Agent | TA 的"天职" (只关心) | TA 的"豁免权" (不关心) |
|---|---|---|
| **Story Planner** | 故事的**骨架**是否足够非线性？分支逻辑是否合理？ | 每个节点的具体对话写得怎么样？ |
| **Node Writer** | 当前这个节点的**对话**是否生动？氛围是否到位？ | 整个故事的结构是否完美？ |
| **Story Reviewer**| 整个剧本是否存在**客观缺陷**（如死胡同、角色矛盾）？ | 故事的创意是否足够惊艳？ |

通过这种方式，我们将一个巨大而模糊的"创作任务"，拆解成了三个小而美的、高度聚焦的子任务。这不仅降低了单个 Agent 的心智负担，也使得整个系统的行为变得**可预测、可管理、可优化**。


## 第三章：Story Planner 的设计哲学 —— 为什么是 ToT？

在三个角色中，**Story Planner** 是最具挑战性的。它是整个系统的"大脑"。

### 1. 为什么普通的 Prompt 搞不定非线性规划？
只看单次 LLM 调用，其本质是"预测下一个 token"，如果没有设计良好的上下文工程 (Context Engineering)，那么注定只能进行**线性**的思维方式。但设计非线性剧本需要**全局思维**和**回溯能力**——"如果我在这里设置分支，会导致结局收不回来吗？"

### 2. 引入 Tree of Thoughts (ToT) 范式：从"棋手思维"中获取灵感

如何让一个天生"向前看"的模型学会"向四周看"？我们从 AlphaGo 的棋局推演中获得了关键灵感。

顶尖的围棋手在落子之前，并不会只看眼前的一步。他们会在脑中构建一棵庞大的"决策树"：如果我下在这里，对手可能会怎么应对？每一种应对之后，我又该如何反击？他们通过模拟多种可能性，评估每条路径的优劣，最终才选择那一步"最优解"。

**Tree of Thoughts (ToT)** 范式正是这种"深思熟虑"过程的工程化实现。我们没有奢望让 Planner 一步到位给出完美答案，而是将"规划"这个复杂任务拆解为三个目标明确、循序渐进的阶段：

#### Round 1: Generate (发散 —— 头脑风暴)

-   **做什么？** 我们不急于让 AI 动笔画蓝图。第一步，先让它提出 3 个**截然不同**的故事方向（我们称之为 `CandidatePath`），比如"一个关于复仇的故事"、"一个关于救赎的故事"、"一个关于阴谋的故事"。
-   **为什么这么做？** 这是为了打破 LLM 的"路径依赖"。我们观察到，如果直接让 AI 生成故事，它往往会"锁定"在它想到的第一个点子上。通过强制要求它产出多个**差异化方案**，我们为创造力打开了更大的可能性空间，也避免了"第一印象偏见"。

#### Round 2: Evaluate (评估 —— 制作人评审会)

-   **做什么？** 这一轮，AI 需要切换角色，从"创意提案者"变成"冷酷的制作人"。我们定义了一套**量化评分标准**——`dramatic`（戏剧性）、`characterFit`（角色契合度）、`branchPotential`（分支潜力）、`thematicDepth`（主题深度）——让 AI 像打分表一样，逐一评估自己在 Round 1 中提出的方案。
-   **为什么这么做？** 这是 ToT 范式的精髓所在——**自我批判（Self-Criticism）**。AI 不再是凭感觉做选择，而是必须依据我们预设的"好故事"标准进行**理性判断**。这个过程将我们对非线性叙事的价值观（如"分支必须有潜力"），显式地注入到了决策过程中。

#### Round 3: Expand (收束 —— 蓝图绘制)

-   **做什么？** 在选定最优方案后，集中所有"算力"，将这个高层概念展开为一张详细的、包含所有节点和连接关系的**故事蓝图**（`NarrativePlan`）。
-   **为什么这么做？** 经过前两轮的"发散"与"筛选"，此时 AI 的目标已经变得非常明确：它知道要讲一个什么样的故事，核心冲突是什么，可能的结局有哪些。在这种高度聚焦的状态下，AI 可以更专注地完成结构设计，而不会再有方向上的摇摆和犹豫。

通过这三轮调用，我们成功地将人类"深思熟虑"的思维模式，移植到了一个本质上进行"线性预测"的语言模型身上。

### 3. Schema 的深层设计意图：用 `PlanNode` 编码"叙事学原理"

ToT 提供了思考的框架，但真正让规划"落地"的，是我们对核心数据结构 `PlanNode` 的精心设计。

我们意识到，Schema 不仅仅是一个"数据容器"，它更是一种**"思维引导"**。通过在 Schema 中设置特定的字段，我们可以**强迫** AI 在生成时思考某些它本不会主动思考的问题。`PlanNode` 的每一个字段，都是我们植入给 AI 的一条"叙事学原理"。

#### 3.1 `functionTag`：用"节拍器"对抗"流水账"

-   **我们遇到的问题**：在早期测试中，AI 生成的故事结构非常"平"。十几个节点，全是"事件 A 发生了，然后事件 B 发生了，然后事件 C 发生了"，缺少节奏感，像一杯温吞水。
-   **我们的反思**：人类剧作家在创作时，会下意识地遵循"三幕剧"、"英雄之旅"等叙事理论。他们知道故事需要有铺垫、有冲突、有高潮、有解决。AI 缺乏的正是这种对"故事节奏"的元认知。
-   **我们的建模**：我们将经典叙事理论中的功能标签抽象出来，形成了一个枚举：`setup`（铺垫）, `rising`（上升）, `conflict`（冲突）, `twist`（转折）, `climax`（高潮）, `falling`（下降）, `resolution`（收束）。在生成 `PlanNode` 时，我们**强制要求** AI 为每个节点打上一个 `functionTag`。
-   **它如何改变 AI 的行为**：这相当于给了 AI 一个"节拍器"。它在放置每一个节点时，必须停下来思考："这个节点在整个故事中扮演什么角色？它是在铺垫，还是在推向高潮？"这种强制性的"自问"，引导 AI 自然地构建出有起伏、有节奏的叙事结构。

#### 3.2 `choicesMeta`：系统的"灵魂字段"，对抗"伪非线性"

-   **我们遇到的问题（也是本项目最核心的挑战）**：AI 非常擅长"假装"在做非线性叙事。它会在故事的最后抛出一个选择题："你是选择 A 还是选择 B？"然后通向两个略有不同的结局。这就是我们反复提到的**"伪非线性"**——分支不影响过程，只影响结局。更糟糕的是，AI 还喜欢设计一些毫无意义的选项，比如"今天中午吃米饭还是面条？"——这种选择对剧情没有任何影响。
-   **我们的反思**：一个好的选择，必须满足什么条件？我们调研了大量优秀的非线性游戏，总结出三个关键要素：
    1.  **情感上有重量**：玩家在做选择时，应该感受到压力或纠结。
    2.  **逻辑上有后果**：选择必须导向不同的剧情发展，而不仅仅是不同的结局画面。
    3.  **类型上有区分**：有些选择改变的是整个故事路线，有些选择改变的是人物关系，它们的性质是不同的。
-   **我们的建模（`choicesMeta` 的诞生）**：为了将这三个要素强制注入 AI 的思考过程，我们为分支节点设计了一个复杂的元数据结构 `choicesMeta`：
    -   `emotionalWeight` (情感重量)：强制 AI 回答："这个选择对玩家来说，是**轻松**、**沉重**，还是**痛苦抉择**？"
    -   `branchType` (分支类型)：这是实现**真正非线性**的核心武器。我们定义了四种分支类型，强制 AI 进行分类：
        -   `route`（路线分支）：这个选择会导向**完全不同的故事线**，后续的场景和遭遇都会改变。
        -   `relationship`（关系分支）：这个选择主要影响与**特定角色的关系**发展。
        -   `information`（信息分支）：这个选择决定玩家**获得什么信息或视角**。
        -   `ending`（结局分支）：这个选择**直接决定**走向哪个结局。
    -   `consequenceHint` (后果暗示)：要求 AI 像游戏设计师一样思考："我应该如何给玩家一个恰到好处的提示，让他知道这个选择很重要，但又不剧透具体后果？"
    -   `impactDescription` (影响描述)：要求 AI 用一句话写清楚这个选择将如何影响后续剧情。
-   **它如何改变 AI 的行为**：`choicesMeta` 的存在，将 Story Planner 的任务从简单的"连接节点"，升华为了**"设计有意义的互动体验"**。当 AI 被迫为每个分支选项填写 `branchType` 时，它必须思考："这个选择到底改变了什么？"如果它发现自己只能填 `ending`，它就会意识到这可能是一个"伪非线性"的设计，从而被引导去思考如何在故事更早的阶段引入 `route` 类型的分支。

通过 `functionTag` 和 `choicesMeta` 的精巧设计，我们成功地将抽象的"叙事学原理"编码进了数据结构，引导一个"线性思考者"学会了像结构设计师一样进行"网状规划"。

## 第四章：Node Writer 的设计哲学 —— 在"效率"与"连贯"间走钢丝

当 Story Planner 画好故事的"骨架"后，接力棒传到了 Node Writer 手中。它的任务是为每一块骨头填充"血肉"——生动的对话、沉浸的旁白、扣人心弦的选项文案。

### 1. 我们遇到的核心矛盾：依赖性 vs 并行性

一个非线性故事可能有 15-20 个节点。如果我们让 Node Writer **串行**地一个一个写，每次 LLM 调用需要几秒到十几秒，整个流程将变得漫长得难以忍受。

**能不能并行生成？** 我们最初尝试了"全并行"方案：把所有节点一股脑扔给 Node Writer，让它同时生成。结果是灾难性的——

-   **问题**：节点 `scene-3` 的开头写道："经历了刚才的争吵，她的情绪还没有平复。" 但问题是，这里的"刚才的争吵"发生在 `scene-2`。当 `scene-3` 被并行生成时，它根本不知道 `scene-2` 写了什么！AI 只能凭空捏造一个"争吵"的细节，结果与 `scene-2` 的实际内容南辕北辙。
-   **教训**：完全的并行会导致**上下文断裂**，故事的连贯性荡然无存。

### 2. 解法：拓扑排序 + 分层并行 + `summary` 传递

我们意识到，节点之间存在天然的**依赖关系**：只有当"父节点"的内容确定后，"子节点"才能知道"之前发生了什么"。但这并不意味着我们只能串行——**同一层的节点之间是没有依赖的，它们可以并行！**

```
        ┌───────────────┐
        │    START      │  ← Layer 0 (先生成)
        └───────┬───────┘
                │
        ┌───────▼───────┐
        │   Scene 1     │  ← Layer 1 (等 Layer 0 完成后生成)
        └───────┬───────┘
                │
        ┌───────▼───────┐
        │   Branch 1    │  ← Layer 2
        └───┬───────┬───┘
            │       │
    ┌───────▼───┐ ┌─▼───────┐
    │  Scene 2A │ │ Scene 2B│  ← Layer 3 (Scene 2A 和 2B 可以并行！)
    └───────────┘ └─────────┘
```

-   **流转逻辑**：
    1.  系统首先对所有节点进行**拓扑排序**，将它们划分为多个"层级 (Layer)"。
    2.  **逐层生成**：只有当 Layer N-1 的所有节点都生成完毕后，才开始生成 Layer N。
    3.  **层内并行**：同一层内的所有节点可以**并发调用** Node Writer，大幅缩短总耗时。

### 3. `summary` 字段：上下文传递的"接力棒"

分层解决了并行的问题，但还有一个问题：Layer N 的节点如何知道 Layer N-1 发生了什么？

-   **方案**：我们在 `NodeDraft` Schema 中设计了一个关键字段：`summary`（一句话摘要）。
-   **机制**：
    1.  当 Node Writer 写完一个节点后，它必须输出一个 `summary`，例如："主角与女主角在天台发生激烈争吵，女主角愤然离去。"
    2.  当生成下一层节点时，系统会将其"父节点"的 `summary` 作为 `previousNodeSummary` 字段注入到 Prompt 中。
    3.  Node Writer 在撰写新节点时，就能从 `previousNodeSummary` 中获知"之前发生了什么"，从而保证剧情的连贯性。

-   **示例**：
    ```
    节点 A (Layer 1) 生成完毕
      └─ 输出 summary: "主角发现了隐藏在书房里的神秘日记本。"
                │
                ▼ (作为 previousNodeSummary 传递给 Layer 2)
    节点 B (Layer 2) 开始生成
      └─ Node Writer 的 Prompt 包含：
         "前序剧情摘要: 主角发现了隐藏在书房里的神秘日记本。"
      └─ 于是 Node Writer 可以写出：
         "你小心翼翼地翻开日记本，泛黄的纸页上记录着一段不为人知的往事..."
    ```

-   **意义**：`summary` 字段就像接力赛中的"接力棒"。它将一个节点的核心信息，精炼地传递给下一个节点，既保证了**生成效率**（通过并行），又确保了**剧情连贯性**（通过上下文传递）。这是一个在"工程效率"与"叙事质量"之间取得精妙平衡的设计。

## 第五章：Orchestrator 的诞生 —— 从"线性脚本"到"状态机"

到目前为止，我们有了三个各司其职的 Agent。但如何将它们优雅地组织起来？

### 1. 为什么不能用简单的线性调用？
最直接的想法是写一个线性脚本：`planner.run() -> writer.run() -> reviewer.run()`。
但在第一次测试中，我们就遇到了致命问题：
* **问题**：Reviewer 审阅后发现 `overallScore: 58`，剧本质量不合格。怎么办？
* **线性脚本的困境**：整个流程结束了，无法回头。难道要让用户重新生成一次，再祈祷下一次运气好？这不叫"系统"，这叫"开盲盒"。

### 2. 引入 Plan-and-Execute 状态机
- **思考**：一个真实的项目经理是如何工作的？他不会等到项目彻底失败才介入，而是在每个阶段结束后进行决策：是进入下一阶段、打回重做、还是终止项目？
- **设计推导**：这个"决策过程"就是一个**状态机**。我们将整个创作流程抽象为一系列状态（`PLANNING`, `WRITING`, `REVIEWING`, `FAILED`, `DONE`）和状态之间的转移条件。
- **Orchestrator 的角色**：它不是一个 LLM Agent，而是一个**确定性的工作流控制器**。它负责：
    1.  **调用 Agent**：在每个状态下，调用对应的 Agent 执行任务。
    2.  **管理数据**：将上一个状态的输出（如 `NarrativePlan`）作为下一个状态的输入。
    3.  **决策流转**：根据 Agent 的输出（如 `CriticReport`）决定下一个状态是什么。

```
          ┌─────────────────────────────────────────┐
          │                                          │
          ▼                                          │
┌──────┐     ┌──────────┐     ┌───────────┐        │
│ INIT │────►│ PLANNING │────►│  WRITING  │        │
└──────┘     └──────────┘     └─────┬─────┘        │
                   ▲                  │              │
                   │                  ▼              │
                   │            ┌───────────┐        │
                   │            │ REVIEWING │        │
                   │            └─────┬─────┘        │
                   │                  │              │
                   │    ┌─────────────┼────────────┐ │
                   │    │             │            │ │
           打回重写 │ critical/score<60  score>=60 │ 通过
                   │    │             │            │
                   │    ▼             ▼            ▼
                   │ ┌──────┐   ┌───────────┐  ┌──────┐
                   └─┤FAILED│   │ REWRITING │  │ DONE │
                     └──────┘   └─────┬─────┘  └──────┘
                                      │
                                      └────────────────► WRITING
```

- **意义**：通过引入状态机，我们的系统获得了**自我修正**的能力。当 Reviewer 发现问题，Orchestrator 可以决定是**全局重写**（退回到 `PLANNING`），还是**局部修正**（进入 `REWRITING` 状态，只让 Node Writer 重写特定节点）。这让系统从一个"一次性"的脚本，变成了一个可持续迭代的"工厂"。

## 第六章：Story Reviewer 的进化 —— 从"主观评价"到"客观证据"

系统有了自我修正的能力，但修正的依据是什么？

### 1. 为什么"让 AI 评价 AI"是不可靠的？
- **思考**：我们最初的 Reviewer Prompt 是："请为这个剧本打分，并给出修改意见。"
- **发现**：LLM 很容易陷入"彩虹屁"模式，给出诸如"故事很精彩，节奏很棒"这样空洞的评价。或者，它会随机找一些无关紧要的细节进行批评。这种反馈毫无价值。
- **洞察**：人类编辑在审稿时，依靠的是**客观分析工具**：大纲视图（检查结构）、字数统计（检查节奏）、角色出场表（检查人物弧光）。他们不是"感觉"有问题，而是"看到"了问题。

### 2. 引入 Reasoning + Acting (ReAct) 范式
- **设计推导**：要让 Reviewer 变得可靠，就必须让它的评价基于**证据（Evidence）**。我们不能只让它"读"，还要让它能"分析"。
- **工具的诞生**：我们为 Reviewer 开发了一套工具箱：
    - `validate-structure`: 运行图算法，检查是否存在**孤立节点**或**死胡同**。
    - `analyze-paths`: 枚举所有从开始到结局的路径，计算**分支多样性**。
    - `analyze-dialogue-quality`: 统计每个节点的**对话数量**。
- **ReAct 的本质**：Reviewer 的工作模式从"一步到位"变成了"侦探破案"：
    1.  **Thought (思考)**："我应该先检查结构是否完整。"
    2.  **Action (行动)**：调用 `validate-structure` 工具。
    3.  **Observation (观察)**：看到工具返回 `deadEnds: ["scene-3"]`。
    4.  **Thought (再思考)**："OK，我找到了一个致命的结构问题。接下来我再看看分支设计得怎么样……"
- **意义**：ReAct 范式将 Reviewer 从一个"主观的文学评论家"转变为一个**"客观的数据分析师"**。它的每一条批评，背后都有工具返回的数据作为支撑。

### 3. Schema 的再进化：CriticReport
为了承载这些"证据"，我们设计了 `CriticReport` Schema：
- **`scores` (多维度评分)**：
    - *设计初衷*：将"好/坏"的模糊感觉，拆解为 `plotCoherence`、`characterConsistency`、`branchDistribution` 等多个可量化的维度。
    - *数据来源*：每个维度的分数都直接或间接地来自工具的输出。
- **`issues[]` (问题列表)**：
    - *设计初衷*：将抽象的扣分项，落实到具体的问题上。
    - *建模*：每个 `Issue` 都包含 `type` (问题类型)、`severity` (严重等级)、`nodeIds` (问题节点)、`description` (描述) 和 `suggestion` (修改建议)。
    - *作用*：这使得反馈变得**精确且可操作**。Orchestrator 可以根据 `severity` 为 `critical` 的 `structure` 问题做出"必须重写"的决策。

## 结语

IntelliVNG 的多智能体系统的概念设计与优化过程，其实也是 [程序化叙事生成（Procedural Narrative Generation）](https://www.psyxel.com/ai-and-narrative-pcg/) 在智能体技术栈下的一次工程实践。

我们通过 `WorldBible` 确立边界，通过 `CharacterDB` 注入灵魂，通过 `ToT 机制` 赋予逻辑，并且处处通过精细的 `Schema` 编织成网。

这套系统的价值，不仅在于它能自动创作游戏剧本，更在于它探索了一种人机协作的新范式：**人类定义规则、边界与协作流程，AI 在这个框架内扮演不同的专业角色，进行探索、创作与自我审视。**
